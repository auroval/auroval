# Q4 — which configuration format?

Status: **open, for the maintainer**. This document presents the choice; it does
not make it. PRD open question Q4.

The PRD's original reason for hyprlang was consistency with Hyprland. That
reason no longer points where it did, so the question is not "hyprlang or not"
but **what consistency is worth being consistent with**.

## What is actually true now

Checked on the target machine, 2026-11-07.

- **Hyprland has a Lua configuration subsystem, shipped.** `hyprland` 0.57.1
  installs `/usr/include/hyprland/src/config/lua/` containing `ConfigManager`,
  `LuaBindings`, `LuaEventHandler`, `LuaCaller`, `LuaRef` and a `bindings/`
  directory. This is not a plan; it is in the package.
- **hyprlang is not gone.** `hyprlang` 0.6.8 is still required by `hyprland`,
  `hyprlock`, `hypridle`, `hyprpaper`, `hyprcursor`, `hyprtoolkit` and
  `xdg-desktop-portal-hyprland`. Deprecated is not removed.
- **On this machine the compositor is already Lua.** `~/.config/hypr/hyprland.lua`
  is the live entry point, `require`-ing six playbook-managed modules under
  `lua/`. Its own header reads: *"Migrated from hyprland.conf (hyprlang) —
  deprecated since Hyprland 0.55 and scheduled for removal. hyprland.conf is
  left on disk, ignored, as a rollback artefact."* `hyprland.conf` was last
  touched in June; the Lua modules as recently as today.
- **The palette is already a Lua table.** `lua/colors.lua` is generated by
  matugen on every wallpaper change and `return`s a table of bare hex strings.
  This is the `theme` component's output, and every other component is supposed
  to consume it.
- **The only live hyprlang left here is `hyprlock.conf`** — and `greet` exists
  to replace hyprlock.

So "consistent with Hyprland" now means Lua. Choosing hyprlang would make
`greet` consistent with the one component the project intends to retire, in a
language the compositor has deprecated.

## The complication, which is not a detail

The PRD lists as a non-goal:

> **No theme marketplace, no scripting language in the config.** hyprlang
> describes a look; it does not run.

Lua runs. That is not an incidental mismatch — it has the same security basis
that `docs/ideas.md` identified as the strongest argument for WebAssembly
themes:

> a theme obtained from the internet would be running inside a greeter, a
> pre-authentication process on a locked screen. [...] an embedded scripting
> language hands over the whole process.

So the two halves of the project's own documents pull opposite ways: consistency
says Lua, and the greeter's threat model says nothing that executes.

There is a second pull in the other direction. The thesis says a theme
determines *"hoe die switchen"* — how backgrounds switch. That is behaviour, not
data, and `ideas.md` is explicit that no configuration format expresses it. A
purely declarative format leaves the thesis partly unimplementable; an
executable one implements it and opens the surface above.

## The options

### A. hyprlang

- **For** It does not execute, which satisfies the non-goal directly. Identical
  to `hyprlock.conf`, so the two surfaces share a dialect during the transition.
- **Against** C3 stands: the package ships only `hyprlang.hpp` with no
  `extern "C"`, so Rust must reimplement the parser or bridge C++. The
  third-party `hyprlang` crate is unendorsed and its licence, maintenance and
  parity are still unverified. Consistent with a deprecated language and a
  component being replaced. Cannot express how backgrounds switch.

### B. Lua, via `mlua`

- **For** Matches the compositor as actually run here. Can `require`
  matugen's `colors.lua` directly — no parser, no second template, no
  translation layer between the `theme` component and its consumers. Expresses
  switching behaviour, which the thesis requires and no declarative format
  provides. Mature Rust bindings, so no parser debt at all.
- **Against** Contradicts a stated non-goal, in a pre-authentication process on
  a locked screen. A theme becomes code, and "customisation means authoring a
  theme" then means "customisation means shipping code" — which is a different
  and larger promise than tenet 1 made.

### B′. Lua, sandboxed

Lua syntax and a Lua-shaped palette, but the interpreter is created without
`io`, `os`, `package` or `debug`, with an instruction-count limit and a memory
cap. Used declaratively — a theme returns a table — while still permitting a
switching function.

- **For** Keeps B's consistency and its ability to express behaviour, while
  closing most of what makes executing a downloaded theme alarming. Strictly
  less capable than the WebAssembly idea in `ideas.md`, and available now
  rather than parked.
- **Against** A sandbox is a claim that has to be maintained, and "no scripting
  language in the config" becomes "a scripting language we believe is contained".
  That is a weaker and more expensive guarantee than a format that cannot run.

### C. Neither — the project's own declarative format

TOML, KDL or a small bespoke one.

- **For** No execution, no parser debt, no dependency on another project's
  direction. Honest about `greet` being its own thing.
- **Against** Consistent with nothing, and adds a third dialect to a machine
  that already has two. Still cannot express how backgrounds switch. The palette
  needs a second matugen template, so the `theme` component now emits two
  formats and they can disagree.

## What this decision gates

- **C3** only matters under option A. Under B and B′ the reimplement-or-bridge
  question disappears.
- **The `theme` component's output format** — one generated palette consumed by
  every component, or one per dialect.
- **`docs/ideas.md`** — if B′ ships, the WebAssembly idea's strongest argument
  (sandboxed executable themes) is partly spent, and what remains for WASM is
  the harder isolation guarantee rather than the capability itself. That is an
  argument for keeping WASM parked, not for pulling it forward.
- **The non-goal itself.** B and B′ require it to be rewritten rather than
  quietly bent. If the answer is Lua, the PRD should say so in that section
  explicitly, with the threat model it accepts.

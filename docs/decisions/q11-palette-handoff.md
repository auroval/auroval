# Q11 — how does the palette reach the greeter?

Status: **decided — option A, the palette inline in the theme.** Chosen by the
maintainer on 2026-11-22. The sub-question at the end — one palette per theme
or one per candidate — is **still open**, and it is not hypothetical: see the
measurement there. Written 2026-11-22
because the last unticked box of P1 (#18) turns out to rest on it, and because
the item that was supposed to answer it is not merely unbuilt but aimed at the
wrong thing.

P1's scope carries this line:

> Palette consumed directly from matugen's `colors.lua` — one generated
> palette, no translation layer.

That line blocks R11's colour half, and R11 blocks *"SDDM comes off the
machine"*, which is the PRD's own success metric for P1. So this is not a
detail at the edge of the phase; it is the phase's last door.

## What is actually true now

Measured on the target machine, 2026-11-22.

- **`/etc/auroval/greet.lua` exists, and declares no palette.** Corrected
  2026-11-22, a few hours after this document first claimed the directory was
  empty. It is not. The file has been there since 2026-11-08 22:33, root-owned
  and world-readable, and it configures a pool of **two** scenes with their R9
  chains. What it carries is no `palette` table, so `absorb` leaves that field
  untouched and `Palette::default()` is in force — the greeter is running
  hyprlock's Catppuccin colours, which is exactly what `theme.rs` says that
  default is for: *"This is a placeholder"*.

  **Where the wrong claim came from**, because the shape of the mistake is
  worth more than the correction: from a journal line, `/etc/auroval/greet.lua:
  not read`, logged by a real greetd start at **13:29** on 2026-11-08 — nine
  hours before the file was written that evening. A dated observation was read
  as present state, and `cat` on the path would have settled it in one command.
  Everything else in this document was measured against something live.

  The conclusion does not change and its reason does: the palette is missing
  **from a file that exists and is already read**, not missing along with the
  file. That makes the fix smaller than this document first said, and the
  sub-question at the end bigger — see both below.
- **The Lua side already accepts a palette.** `config.rs` reads a
  `palette = { role = "rrggbb" }` table out of the theme, flattens it, and
  hands it to `Palette::parse`. There is no missing mechanism here, and no
  translation layer to write: it is built, tested and unused for want of a
  file.
- **`Palette::load` also exists**, reading a file of `role = hex` lines. It is
  `#[allow(dead_code)]` and nothing calls it.
- **matugen 4.2.0 is installed** and writes `~/.config/hypr/lua/colors.lua`,
  fifteen lines, regenerated by `awww-wallpaper.sh` on every wallpaper change.

## The complication, which is not a detail

**That file is in a home directory.** R15 says no media path reads from a
user's home, and C10 is the reason: the greeter runs as its own unprivileged
user and cannot traverse a home at mode `0700`. The one file P1's line names
is the one file the greeter is structurally unable to read. Nothing about the
sandbox needs discussing before that is dealt with.

## And a second one: the two formats look alike and are not

This was measured rather than assumed, because the shapes are close enough to
fool a reader. `Palette::parse` takes `role = rrggbb` lines. matugen's template
emits a Lua table:

```lua
return {
    primary    = "f9b1dc",
```

Running the real file through the real parser:

```
parsed primary  = [0.5372549, 0.7058824, 0.98039216, 1.0]
default primary = [0.5372549, 0.7058824, 0.98039216, 1.0]
IDENTICAL TO DEFAULT: true
```

Every line is skipped — the value carries its quotes and its trailing comma, so
`hex()` sees nine characters and returns `None`, and the loop's `continue` eats
it. The result is not an error. It is `Palette::default()`, silently, which
looks exactly like "no theme installed". That is the worst failure shape
available: the one that is indistinguishable from the state you were already
in. Any option that reads matugen's output as text has to deal with this, and
dealing with it is a translation layer by any honest name.

This also retires one of Q4's three stated reasons for choosing Lua —
*"matugen already emits the palette as a Lua table that a Lua config can
consume with no parser in between"*. It does not, on either half: not through
Lua, because the sandbox denies the include; and not as text, per the run
above. The two consistency arguments Q4 also gave are untouched and still carry
that choice, which is why this is a correction to the reasoning and not a
reopening of Q4.

## The line is not only unachievable, it is superseded

Two separate reasons, and the second is the one that matters.

**It cannot be done as worded.** Lua's mechanism for one file including another
is `require`/`dofile`. R22's sandbox denies both and never opens `package`, on
purpose and with its own test that it cannot be reassembled from inside. So a
`greet.lua` cannot include a `colors.lua`.

**And it should not be done at all.** `nightshade.md` §4.4 is a later and
measured document, and it settles the opposite:

> the palette is derived once per scene, from one canonical frame, when the
> theme is packaged. It ships with the scene.

with the consequence stated plainly in the same section: *"matugen moves from
runtime dependency to packaging tool."* Live re-derivation on wallpaper change
is a thing §4.4 deliberately gives up, so that the greeter, the lock screen and
the desktop are byte-identical on colour rather than approximately equal — and
§4.3 wants only the *hue* from the media anyway, with tone and chroma from the
theme. Consuming matugen's live output would take the pastel the theme exists
to reject: §4.3's worked example turns matugen's `#ffb0cd` (C\* 33) into
`#ff1296` (C\* 85.4).

P1's line predates all of that. It should be reworded rather than built.

## What this gates

Three half-ticked requirements, all on the same missing file:

- **R11's colour half** — "colour from the active theme". Geometry and
  typography were measured to the half-pixel on 2026-11-08; the colour half has
  nothing to compare against because `Palette::default()` is in force.
- **R15's own criterion** — a configured background still rendering with
  `/home/<user>` at mode 700. There is no configured background to render.
- **R9's third clause** — *still logs in*. It wants a greetd sitting with a
  video background configured and the plugins held back.

## The options

### A. Inline in the theme's own `greet.lua`

The palette table ships in the theme, derived at packaging time per §4.4.
Nothing new is built: `config.rs` already parses it, and the theme is already
the file the greeter reads.

- **For** Zero mechanism. It is the shape §4.4 asks for. One file to install,
  which is the file that has to be installed anyway.
- **Against** Palette and background live in one table while the background is
  a *pool* — see the sub-question below.

### B. A second file, `/etc/auroval/palette.conf`, read by `Palette::load`

The dead code that already exists, pointed at a file beside the theme.

- **For** The palette can be regenerated without rewriting the theme, which
  matters if anything ever does re-derive at runtime.
- **Against** Two files that must agree, and §4.4 says the palette is a
  property of the scene — so the thing that would rewrite it would also be
  rewriting which scene is installed. It solves a problem §4.4 removed.

### C. The host injects a palette global before the theme runs

Rust reads a palette from somewhere, sets it as a global, and the sandboxed
theme reads it as a variable.

- **For** A theme could *compute* with the palette — derive a scrim strength,
  tint something — rather than only declare it.
- **Against** It widens the sandbox's contract, and nothing asks for the
  computation yet. It is the right answer to a question nobody has.

### D. Live matugen `colors.lua`, as P1's line says

- **Against** Everything above: it is in a home (R15, C10), it parses to the
  default in silence, it needs `dofile` the sandbox denies, and §4.4 gives up
  live re-derivation on purpose.

## Recommendation

**A, and reword P1's line to match §4.4.**

Then, to unblock the three requirements this gates, the smallest honest step is
not a mechanism at all and is smaller than this document first said: **add a
`palette` table to the `/etc/auroval/greet.lua` that is already there**,
derived from the canonical frame of the scene it already points at. Theme
packages (#5) do not exist yet and this does not wait on them — an installed
theme package would put the same table in the same file.

`deploy/greet.lua` is that file, under version control, installed by hand like
the PAM lines in TRIAL.md §1 and for the same reasons. Run through the real
`Config::load`, it reports no problems, keeps its R9 chain, and yields
`primary = 00bcd0` against the default's `89b4fa` — which is the check the
measurement below says not to skip.

## The sub-question this opens, and it is a real one

`background` is a **pool** of candidates and `rotation` picks one per launch.
`palette` is a single table on `Config`. So a theme with two scenes shows
scene-05's picture under scene-01's accent on half its boots, and the
disagreement §4.4 exists to prevent comes back through the other door — not
between surfaces this time, but between the picture and the chrome on one
surface.

Two shapes, neither measured:

- A palette per candidate, so the pool carries `{ background = …, palette = … }`
  rather than a path. Honest, and it changes a config shape that themes already
  write.
- One palette per theme, with rotation confined to scenes that share a hue.
  Cheaper, and it makes "a theme" smaller than nightshade currently assumes:
  §4.4's own two-scene example is the case that breaks.

**And this machine already ships two**, which is the half of the correction
that costs something. The pool in `/etc/auroval/greet.lua` is scene-01 and
scene-05, and they do not share a hue. Measured 2026-11-22 with
`tools/scene-check/scene_check.py` against the installed stills:

| scene | hue | `primary` | C\* |
|---|---|---|---|
| nightshade-01 | 213.5° | `00bcd0` — cyan | 38.4 |
| nightshade-05 | 38.7° | `ff3522` — red-orange | 93.5 |

A 175° swing, and §4.3.1 had already named the floor of that trough: 213° is
cyan, where no choice of lightness can make an accent neon, while 38.7° is in
the band where it cannot help but be. One `palette` table cannot serve both, so
with both in the pool **half of all boots show the lantern under a cyan
accent** — the disagreement §4.4 derives at packaging time to prevent, arriving
through the other door.

So the sub-question is live rather than hypothetical, and the recommendation
carries one more line with it: **the pool goes to one candidate** until the
sub-question is answered. `deploy/greet.lua` leaves scene-05 commented out,
with these numbers in the comment, so that nothing is lost and uncommenting it
is how you see the fault.
